# Upgrading a decomp to a newer skill version

A repo this skill started keeps its tools and template files in step with the skill. An upgrade
brings a repo from the skill version it is at to a newer one. The decomp's own work is never touched:
`src/`, `tests/` cases, names in `functions.txt`, `globals.txt`, `symbols.txt`, the rules in
`models.txt`, `docs/`, the engine notes.

## Versions

A version is a tag (`v0.6`) or a dev version: a commit after the last tag, written
`<last tag>+<short commit>` (`v0.6+a1dd632`). For the skill's git checkout:

```
git describe --tags --exact-match 2>/dev/null || echo "$(git describe --tags --abbrev=0)+$(git rev-parse --short HEAD)"
```

A zip install has no git: its `VERSION` file holds the same string (`zip.sh` writes it). An upgrade
needs the skill's history, so with a zip install clone the skill's repo first (Getting the tools).

The repo records its version in `KICKOFF` (one line). Every upgrade, and every hand sync of tools or
template files from the skill, rewrites it in the same change: it is what the next upgrade reads to
know what to bring over. It always holds a resolved version: an upgrade to `main` writes
`<last tag>+<commit>`, never `main`.

`unstable` is the one keyword: the repo follows the skill's main branch, synced in the same
change as every skill change, and is never upgraded. Only a person writes it, on purpose; a kickoff
or an upgrade never does, and a missing or unreadable `KICKOFF` is never taken to mean it.

## Steps

1. **The repo's version.** Read `KICKOFF`. `unstable`: stop, the repo is kept current by hand. A repo from before `KICKOFF` existed: the README line
   "autogenerated using dc-decomp-kickoff vX" gives it. With neither, find the last skill commit
   before the repo's first commit (`git log -1 --before=<date of the repo's first commit>` in the
   skill), tell the user it is a guess and confirm it before going on.
2. **The target version.** List the tags (`git tag --sort=-v:refname`) and recommend the latest. Also
   offer `main` as the dev version, with what it adds over the latest tag
   (`git log --oneline <latest tag>..main`). The user picks. Going back to an older version is not an
   upgrade: stop.
3. **Both versions side by side.** `git worktree add <tmp>/from <from commit>` and the same for the
   target (or `git archive`). Every step below compares `<tmp>/from` with `<tmp>/to`, never with
   the working copy of the skill.
4. **Tools** (the repo's copies must be identical to the skill's): every file of the target's tools
   list (SKILL.md step 6: `scripts/...` into `tools/`, `tools-image/`, `hooks/`) is copied over the
   repo's. A tool the target no longer lists is removed from `tools/`; one it adds is copied in.
   A repo whose `tools/` file differs from the from-version's copy has a local edit: show the user
   the diff before overwriting it.
5. **Template files** (the repo has filled their placeholders and may have edited them): `build.sh`,
   `setup.sh`, `disc.sh`, `textures.sh`, `README.md`, `AGENTS.md`, `models.txt` (header comments only:
   the rules are the repo's) and `template/gitignore` as `.gitignore`. Apply the skill's own change
   between the two versions as a patch: `git diff <from> <to> -- template/<file>`, applied to the
   repo's file (`git apply --3way` or `patch`). A new template file is copied in and its placeholders
   filled as at kickoff. A hunk that does not apply is shown to the user with the repo's lines
   around it; never guess a merge of the repo's own wording.
6. **What else changed.** Read the skill's history between the two versions
   (`git log <from>..<to>` and `git diff <from> <to> -- SKILL.md references/`) and work out what the
   target's procedure produces that this repo lacks: a new generated file, a new committed file, a
   pass that names more functions, a changed file format. Do each, keeping the repo's own work (its
   names win over any the pass would add).
7. **Regenerate.** `bash setup.sh <the user's .gdi>` (rewrites `asm/`, `text-map/` and `model-map/`
   with the new tools), then `bash build.sh`: it must print `MATCH`. Then `python3 tools/progress.py`
   and, where the README shows the progress block, that block.
8. **Record and report.** Write the target version to `KICKOFF` (resolved: a tag, or `<last tag>+<commit>` for `main`). Leave everything uncommitted and
   end with one numbered table: each file group (tools, each template file, each change from step 6,
   regenerated outputs, `MATCH`) and what happened to it.
